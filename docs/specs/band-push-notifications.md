# Spec: Band push notifications

> **Status:** in progress (Phase 1 implemented, device validation pending) · **Created:** 2026-09-27 · **Owner:** Renán Díaz
> **Origin:** "push notifications de cuando alguien de la banda agrega un
> show, un setlist, un ensayo, cosas así".
> **Scope:** Web Push to band members when another member creates a show, a
> rehearsal or a (published) setlist; later, when a show or rehearsal is
> moved or cancelled. Opt-in per device, mute per band. No email, no in-app
> inbox (§8). Two phases, three PRs (§10).

This is a design, not code. Signatures and schemas are the contract; no
bodies here.

## 0. Where we are

| Fact | Where | Consequence |
|------|-------|-------------|
| The service worker is generated by Workbox (`generateSW`, `registerType: 'prompt'`) | `vite.config.ts` | No `push` / `notificationclick` handler exists; we add one without leaving `generateSW` (§1 decision 4) |
| `shows`, `rehearsals`, `setlists` carry `user_id` (creator); `requests` carries `created_by` | baseline | The row alone doesn't say who *edited* it (members edit any row, content-permissions spec) — the actor must come from `auth.uid()` in the trigger, not from the row |
| `setlists.is_draft`; `convertDraftToSetlist` flips it to `false` with an UPDATE | `setlistsService.ts` | "A setlist was added" = INSERT with `is_draft = false` **or** UPDATE `true → false` |
| `band_members` has no RLS and no display name; names live in `auth.users.raw_user_meta_data` | baseline | The sender (Edge Function, service role) resolves names; the client never does |
| Edge Functions already run with the service role (`calendar-feed`, `send-invitation-email`) | `supabase/functions/` | Same deployment model; secrets via `supabase secrets set` |
| `isOfflineDownloadsEnabled()` is the pattern for a build/device flag | `src/lib/featureFlags.ts` | Same pattern for rollout (§1 decision 8) |
| `src/lib/platform.ts` detects iOS and "in a browser tab" | offline download UI | Reused for the iOS install requirement (§2.3) |
| `useOpenInBand()` switches band before navigating | `src/hooks/` | A tapped notification must do the same (§1 decision 6) |

## 1. Decisions

1. **Server-side fan-out from database triggers, not from the client.** An
   `AFTER INSERT/UPDATE` trigger on `shows`, `rehearsals`, `setlists` writes
   a row to `notification_events` (an outbox); the outbox INSERT calls the
   Edge Function `send-push-notifications` through `pg_net`. Rejected:
   calling the function from the service after `createShow()` — it misses
   any other write path, doubles the work on retries, and the client could
   send anything. Tradeoff: logic in SQL + a Vault secret to configure; in
   exchange the trigger is the single place that decides "this is an event".
2. **Actor = `auth.uid()`**, read in the trigger (SECURITY DEFINER keeps the
   caller's JWT claims). `NULL` (service role, SQL editor, migrations) →
   no event. The actor never receives their own notification, on any device.
3. **Recipients = every `band_members` row of the band except the actor,
   guests included** (they can view shows and setlists), minus users who
   muted the band (§3.1), joined to their `push_subscriptions`. Membership is
   read at send time, so someone removed between the insert and the send is
   not notified.
4. **Keep `generateSW`; add `workbox.importScripts: ['push-sw.js']`.**
   `public/push-sw.js` holds only `push` and `notificationclick`. Switching
   to `injectManifest` would rewrite the worker that offline mode depends
   on (precache, runtime caching, `ignoreURLParametersMatching`) for two
   event listeners. `push-sw.js` is a `.js` in `dist/`, so it is precached
   and `check-precache.mjs` keeps covering it. It must stay dependency-free
   and must not call `skipWaiting` / `clientsClaim`. Build only: the dev
   worker is an ES module, where `importScripts` throws, so push is tried
   with `npm run build && npm run preview` (PR 1.2).
5. **Web Push with VAPID, no Firebase.** Works on Chrome/Edge/Firefox
   (desktop and Android) and Safari (macOS, and iOS/iPadOS 16.4+ **only for
   the app added to the Home Screen**). The public key is
   `VITE_VAPID_PUBLIC_KEY` (public by design, fine as `VITE_*`); the key pair
   is an Edge Function secret (`VAPID_KEYS`, JWK JSON from
   `npm run vapid-keys`, plus `VAPID_SUBJECT`), never `VITE_*`. The sender
   uses `jsr:@negrel/webpush@0.5.0` (Web Crypto only; `npm:web-push` depends
   on Node crypto APIs), with a fresh `ApplicationServer` (ECDH key pair) per
   message. PR 1.1 checked it against a fake push service: the body decrypts
   the way a browser does (RFC 8291, `http_ece`), the VAPID JWT verifies
   (RFC 8292) and a 410 surfaces as `PushMessageError`. Real Chrome and
   Safari endpoints are the PR 1.1 manual check.
6. **A tap opens the entity in its band.** The payload's `url` is
   `/shows/:id?band=<bandId>` (same for rehearsals and setlists). The worker
   focuses an open app window and `navigate()`s it, else `openWindow()`.
   The app handles `?band=` once, in `AppMain`: if the id is one of the
   user's bands, `setSelectedBand` (only when it differs), then drops the
   param with a `replace`; unknown band → just the path (the detail view
   already handles "not found"). Same rules as `useOpenInBand`, extracted so
   both share them.
7. **Localised on the server by the subscription's locale.** The worker
   can't run i18next and the sender doesn't know the user's language, so
   each `push_subscriptions` row stores `locale` (`en` | `es`, from i18next
   at subscribe time, updated on language change). The strings live in
   `supabase/functions/_shared/pushMessages.ts` (dependency-free, tested from
   `src/lib/__tests__/`, like `ics.ts`).
8. **Behind a flag until the device checklist passes.**
   `isPushNotificationsEnabled()`: `VITE_PUSH_NOTIFICATIONS=true` or
   `localStorage.bandmate_flag_push = "1"`. The flag hides the UI only; the
   triggers run regardless (no subscriptions → nothing is sent).
9. **Every push shows a notification.** Browsers require
   `userVisibleOnly`, and Safari revokes subscriptions that receive silent
   pushes, so the worker can't skip one — not even while performance mode is
   open. Mitigation is copy (§2.2: "Use Focus / Do Not Disturb on stage") and
   Phase 1 only sending low-frequency events.

## 2. UX

### 2.1 Entry point

User menu (`AuthButton`, both variants) → **Notifications** row (only with
the flag, only in `authMode: "session"`, hidden offline; between About and
Check for updates) → opens `NotificationSettingsModal`. The modal is
rendered once by `NotificationSettingsHost` in `App` and opened through
`notificationSettingsStore`: the mobile drawer unmounts the menu when a row is
tapped, so the modal can't live in it.

### 2.2 Settings modal

- **This device:** status line + one button.
  - `unsupported` → "This browser can't receive notifications."
  - `needs-install` (iOS in a browser tab) → "On iPhone and iPad, add
    Bandmate to your Home Screen first" + the existing install hint.
  - `denied` → "Notifications are blocked for Bandmate. Allow them in the
    browser / system settings." (no button: the prompt can't be shown again)
  - `off` → **Turn on** (calls `Notification.requestPermission()` in the tap
    handler — iOS requires a user gesture — then subscribes).
  - `on` → "On for this device" + **Turn off** (unsubscribes, deletes the
    row).
- **Bands:** one switch per band in `bands` ("Notify me about <band>"),
  default on. Saved per user (all devices).
- Footer note: "You won't be notified about your own changes. On stage, use
  Focus / Do Not Disturb."

No permission prompt on app load, ever. A one-time, dismissible nudge on
the dashboard (Phase 2 candidate, not in scope) is the only other place it
may be offered.

### 2.3 The notification

| Event | Title | Body | Opens |
|-------|-------|------|-------|
| show created | `<band> · New show` | `<actor> added "<name>" · <weekday, date> <time?>` | `/shows/:id?band=` |
| rehearsal created | `<band> · New rehearsal` | `<actor> added a rehearsal · <date> <time?> · <location?>` | `/rehearsals/:id?band=` |
| setlist published | `<band> · New setlist` | `<actor> added "<name>" · <n> songs` | `/setlists/:id?band=` |
| show/rehearsal moved (Phase 2) | `<band> · Show moved` | `"<name>" is now <date> <time?>` | same |
| show/rehearsal cancelled (Phase 2) | `<band> · Rehearsal cancelled` | `<date> <time?>` | same |

`tag` = `<type>:<entityId>` so a later event about the same entity replaces
the earlier one instead of stacking; `icon` = `/icon-192.png`. Dates are
formatted in the sender from the stored strings (floating, no zone, same as
`ics.ts`) — never through `new Date()` on a date-only string. Actor name:
`full_name` → `name` → email local part → "Someone".

## 3. Contract

### 3.1 Schema (one migration, `supabase/migrations/<ts>_push_notifications.sql`)

```sql
push_subscriptions (
  id uuid pk default gen_random_uuid(),
  user_id uuid not null references auth.users on delete cascade,
  endpoint text not null unique,
  p256dh text not null,
  auth text not null,
  locale text not null default 'en' check (locale in ('en','es')),
  user_agent text,
  created_at timestamptz default now(),
  last_success_at timestamptz
)
-- RLS: select/update/delete where user_id = auth.uid(); no INSERT policy:
-- rows come from register_push_subscription(endpoint, p256dh, auth, locale,
-- user_agent) (SECURITY DEFINER, authenticated only), which upserts on
-- endpoint and hands it to the caller — the endpoint belongs to the browser,
-- so the account that registers it last owns it

band_notification_mutes (
  user_id uuid references auth.users on delete cascade,
  band_id bigint references bands on delete cascade,
  created_at timestamptz default now(),
  primary key (user_id, band_id)
)
-- RLS: own rows only, INSERT also requires membership of the band;
-- absence of a row = notifications on

notification_events (
  id bigint generated always as identity pk,
  band_id bigint not null references bands on delete cascade,
  actor_id uuid not null,
  type text not null,        -- CHECK: 'show.created' | 'rehearsal.created' | 'setlist.published' (Phase 2 widens it)
  entity_id text not null,
  payload jsonb not null,    -- the fields the message needs, captured at write time
  created_at timestamptz default now(),
  processed_at timestamptz,  -- set when the function claims the event
  recipients integer,        -- subscriptions delivered to
  error text
)
-- RLS enabled, no policies: clients can't read or write it
```

- Triggers: `notify_show_created`, `notify_rehearsal_created` (AFTER
  INSERT; skipped when the date is more than a day in the past or the status
  is completed / cancelled: that is history being entered), and
  `notify_setlist_published` (AFTER INSERT OR UPDATE OF `is_draft`). All
  SECURITY DEFINER with `search_path` pinned, each inserting at most one row
  through `enqueue_notification_event()`, which reads `auth.uid()` and
  swallows its own errors: a notification never makes the write fail.
- Dispatch: `AFTER INSERT ON notification_events` → `net.http_post` to the
  function URL with header `x-push-secret`, both read from Vault
  (`push_function_url`, `push_function_secret`). **Missing secrets, Vault or
  pg_net → the event is kept and nothing is sent**, so `supabase db reset`
  and databases without push keep working. pg_net sends after commit, so a
  rolled-back write sends nothing.
- Checked with `supabase db reset`; the PR notes which policies were
  verified (DoD #6).

### 3.2 Edge Function `send-push-notifications`

Deployed with `--no-verify-jwt` (also `supabase/config.toml`); rejects any
request without the matching `x-push-secret` (constant-time compare, 401).
Input `{ eventId }` only — it re-reads the event, so the body can't inject
content. Steps: claim the event (`UPDATE … SET processed_at WHERE
processed_at IS NULL RETURNING`; no row → return, so replays send nothing)
→ recipients (§1 decision 3, `selectRecipients` in
`_shared/pushRecipients.ts`) →
`buildPushMessage(event, locale, actorName, bandName)` → send to each
subscription (concurrency 10, TTL 24 h, `urgency: normal`) → delete
subscriptions answering 404/410, stamp `last_success_at` on the rest → set
`recipients` (and `error`, first five failures). A crash after the claim
loses that event (no retry in Phase 1; §6). Secrets: `VAPID_KEYS`,
`VAPID_SUBJECT`, `PUSH_SECRET`. Setup: [docs/setup/push-notifications.md](../setup/push-notifications.md).

### 3.3 Shared pure module

```ts
// supabase/functions/_shared/pushMessages.ts
export type PushEventType = "show.created" | "rehearsal.created" | "setlist.published"; // + Phase 2 types
export interface PushMessage { title: string; body: string; url: string; tag: string }
export function buildPushMessage(input: {
  type: PushEventType; bandId: number; bandName: string; actorName: string;
  entityId: string; payload: Record<string, unknown>; locale: "en" | "es";
}): PushMessage;
```

Sign-out (user-initiated, `performUserSignOut`) unsubscribes this device
and deletes its row **before** signing out; otherwise the next person
signing in on a shared iPad receives the previous user's pushes. Not on an
involuntary `SIGNED_OUT` (same rule as the offline wipe: don't add a third
wipe trigger, this is part of the first). `AuthButton` passes
`clearDeviceBeforeSignOut` as the wipe step: `wipeAll()` and
`unsubscribeThisDevice()` in parallel; a failed unsubscribe is only logged
(the sender drops the dead endpoint), a failed wipe keeps its old handling.
Language changes in the user menu call `updateThisDeviceLocale`.

### 3.5 i18n (both locales)

`notifications.menuItem`, `notifications.title`, `notifications.device.*`
(one per status + `turnOn`, `turnOff`), `notifications.bands.title`,
`notifications.bands.toggle`, `notifications.footer`,
`notifications.errors.subscribeFailed`. The push texts themselves are in
`pushMessages.ts`, not in `en.json` / `es.json`.

## 4. Acceptance criteria

Phase 1:

- **AC1** Member A creates a show in band X; member B (subscribed, not
  muted) gets "X · New show" on every subscribed device within ~10 s.
- **AC2** A gets nothing, on any of A's devices.
- **AC3** Same for a rehearsal, and for a setlist created non-draft or
  converted from draft. Creating a draft sends nothing.
- **AC4** Editing, reordering or deleting any of them sends nothing.
- **AC5** B muted band X → nothing for X; band Y still notifies.
- **AC6** Tapping the notification with band Y selected opens the show in
  band X (header and role are X's), app already open or closed.
- **AC7** The text follows the language the device subscribed with (en/es).
- **AC8** An expired subscription (410) is deleted on the next send.
- **AC9** iPhone in Safari tab: the modal says to add to Home Screen; after
  installing, Turn on prompts and AC1 works.
- **AC10** Denied permission shows the "blocked" state, no button.
- **AC11** Sign out removes this device's subscription; signing in as
  another user on it receives nothing for the first user's bands.
- **AC12** A request to the function without the secret gets 401; a replayed
  `eventId` sends nothing twice.
- **AC13** Flag off: no Notifications row; offline mode unchanged
  (`check-precache` passes, the app starts offline).

Phase 2:

- **AC14** Changing a show's / rehearsal's date, time or location notifies
  "moved"; changing only notes, setlist or other fields doesn't.
- **AC15** Status → cancelled notifies "cancelled" (and not "moved").
- **AC16** Several edits to the same entity within 2 min produce one
  notification with the final values.

## 6. Risks

| Risk | Mitigation |
|------|------------|
| Deno Web Push library doesn't interoperate with Safari's endpoints | PR 1.1 spike (§1 decision 5) covers the RFCs; the manual check sends to a real Chrome and an installed iOS PWA |
| Apple rejects VAPID tokens valid for more than an hour; the library signs them for exactly 3600 s | Watch for 403 `BadJwtToken` from `web.push.apple.com` in `notification_events.error`; the fix is signing the JWT ourselves with a shorter `exp` |
| Pushes during a gig (iPad on the stand) | §1 decision 9: copy + only low-frequency events in Phase 1; Phase 2's "moved" is coalesced (AC16) |
| Bulk creation (someone enters ten rehearsals in a row) floods members | Accepted in Phase 1 (one per entity, distinct tags); if it's real in use, Phase 2 adds per band + type coalescing in the same window as AC16 |
| `pg_net` call lost (function down) | The outbox keeps the row with `processed_at` null (or `error` set after a claim); a retry cron is Phase 2 only if losses show up in `notification_events` |
| Shared device keeps the previous user's pushes | AC11 (unsubscribe on voluntary sign-out) |
| The worker file changes but clients keep the old one | `importScripts` files are byte-checked on update; the existing prompt-to-reload flow applies |
| Privacy | Endpoints are personal data: the Privacy page gains a "Notifications" paragraph (what's stored, how to turn it off) in PR 1.2 |

## 7. Owner decisions (2026-09-27)

1. **Requests** (new proposals): not in Phase 1; decided with votes and
   comments in a later phase, since comments are the chatty part.
2. **Guests** are notified by default (they can view everything notified)
   and can mute.
3. **Per band** muting only; per type is added only if users ask.

## 8. Out of scope

In-app notification inbox / bell (the outbox makes it possible later),
email digests, reminders before a show or rehearsal (scheduled, a different
mechanism: cron over upcoming events), notifications for songs, comments
and votes, native apps.

## 10. Phases and PRs

### Phase 1 — notify new shows, rehearsals and setlists

**Goal:** a member who turned notifications on hears about every show,
rehearsal and published setlist another member adds, and one tap opens it in
the right band.
**Closes:** AC1–AC13.
**Validate (manual):** two accounts in two bands; devices: desktop Chrome,
Android Chrome, installed iPhone/iPad PWA. Run AC1–AC11 on each; check the
function logs for AC8/AC12; with the flag off, confirm the offline startup
still works.

- **PR 1.1 — backend** (implemented). Migration (three tables, three
  triggers for the Phase 1 events, outbox dispatch via Vault + `pg_net`,
  `register_push_subscription`), `pushMessages.ts` / `pushRecipients.ts` +
  tests, `send-push-notifications`, `npm run vapid-keys`,
  `docs/setup/push-notifications.md`. Nothing user-visible; validated by
  subscribing a browser by hand (devtools) and inserting rows (setup guide
  §4).
- **PR 1.2 — client** (implemented). `push-sw.js` + `importScripts`,
  `pushSupport`, service, flag, settings modal, user-menu row, `?band=`
  handling, sign-out unsubscribe, Privacy paragraph, i18n, docs. Completes
  the phase. Checked without devices: unit and DOM tests, and a push
  delivered through the DevTools protocol to the built worker in Chromium
  (notification shown with title, body, tag and url). Subscribing against a
  real push service and AC1–AC11 are the device checklist.

### Phase 2 — moved and cancelled events

**Goal:** members hear when a show or rehearsal changes date, time or place,
or is cancelled — the notification that matters most on the day.
**Closes:** AC14–AC16.
**Validate (manual):** edit a show's date twice within a minute → one
"moved" with the final date; cancel it → "cancelled"; edit only notes →
nothing.

- **PR 2.1** — UPDATE branches of the show/rehearsal triggers (compare
  `date`, `time`, `location`/`venue`, `status`), coalescing (the dispatch
  waits for a 2-minute quiet window per `tag`, via `pg_cron` or a delayed
  outbox pick-up — decided in the PR), `pushMessages` types + tests.
